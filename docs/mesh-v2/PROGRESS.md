## Integration cleanup and skill gap analysis — 2026-10-30

- Root cause of the fresh connection 409: `ConnectionService.requestConnection` constructed a new `PENDING` request and then ran the duplicate-state check against that unsaved object. The actual response was HTTP 409, `A connection request is already pending.` The service now checks for an existing persisted request before treating `PENDING` as a duplicate. Existing connection, reverse pending request, and block checks remain in place; focused tests cover the fresh, duplicate, blocked, and already-connected paths. This fixes the legacy personal-connection flow and does not make personal connections a prerequisite for future project recruitment.
- Project creation still sets `DRAFT` explicitly. Requirements can be saved in `DRAFT`; `RECRUITING` and `ACTIVE` require at least one requirement. Owner-only `PUT /projects/{id}/requirements` now allows retention of the current state or forward transitions `DRAFT → RECRUITING → ACTIVE → ARCHIVED`. Invalid transitions return 409. Team size includes the owner and cannot be reduced below current membership.
- Frontend coordination needed: `BlueprintEditor.tsx` defaults the workbench to `RECRUITING` and offers `ACTIVE` directly from a newly created `DRAFT` project. The direct `ACTIVE` selection now receives 409 under the lifecycle contract. `ProjectCreationWizard.tsx` catches a failed requirements save and leaves the newly created project in place with a warning. The frontend-owned files were not changed; the wizard should use `DRAFT` or `RECRUITING` at creation and reserve `ACTIVE` for a subsequent owner transition.
- Added deterministic `GET /projects/{projectId}/skill-gap-analysis`. It reads saved requirements, all confirmed project members, and their self-declared profile skills. Each requirement is `COVERED` when at least one member meets its proficiency, `PARTIAL` when members declare only lower proficiency, or `UNCOVERED` when no member declares it. It separates required and preferred gaps, lists satisfying member IDs, and reports target size, member count, and remaining capacity. Missing requirements return 409; nonmembers receive 403. No GitHub inference, probability, team optimization, or recruitment logic was added.
- Updated `contracts/openapi.yaml` with the endpoint, exact response schemas, and lifecycle transition description.
- Backend suite: 28 tests in 12 suites passed with 0 failures, 0 errors, and 0 skipped. OpenAPI YAML parsed successfully. Mockito still emits its existing dynamic-agent warning.
- Live runtime limitation: the backend still running on port 8080 was built before this assignment. An authenticated request to the new endpoint returned HTTP 500 with `No static resource projects/.../skill-gap-analysis.` That is the old process's generic fallback for an unmapped route. Restart the backend from the updated source, then repeat the authenticated endpoint and connection-request checks against development Supabase. No new database migration is required for this endpoint.

- Added owner-only `POST /projects/{projectId}/team-suggestions` for `DRAFT` and `RECRUITING` projects. The response includes the persisted skill-gap analysis, current member count, remaining capacity, up to three alternative combinations, covered and uncovered skill IDs, candidate explanations, and availability status. It does not write invitations or memberships.
- The deterministic engine uses a beam width of 12 and at most 80 candidates. It reserves at least one qualified specialist per requirement before filling the candidate pool, includes existing members in scoring, uses the highest individual proficiency for each required skill, and evaluates preferred skill contribution separately. Several lower-proficiency students cannot jointly satisfy a required threshold. Results are ordered with stable UUID tie breaking and diversity preference.
- Candidate loading requires onboarded profiles linked to `ACTIVE` accounts and excludes V10 synthetic demo accounts identified by `@mesh.local`. Existing members, explicitly excluded candidates, blocked pairs, and candidates with incompatible declared availability are removed. Missing or incomparable availability is returned as `UNKNOWN`; `REQUIRE_OVERLAP` excludes it. GitHub language evidence is considered only for a self-declared skill meeting its proficiency threshold, and contributes at most five internal ranking points. No success probability is calculated.
- `contracts/openapi.yaml` documents the new request, response, authorization, and errors. Backend tests cover deterministic ordering, conservative required coverage, preferred coverage, alternatives, candidate-pool diversity, blocks, capacity, learning interest, availability policy, owner authorization, and HTTP response validation.
